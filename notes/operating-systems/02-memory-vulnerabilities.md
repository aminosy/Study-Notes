# 常见内存类漏洞：从「机制被破坏」的角度理解内存安全

本篇从操作系统内存机制的**不变量 (invariant)** 出发，梳理常见内存类漏洞的成因与形态：栈/堆缓冲区溢出、use-after-free、double free、整数溢出导致的越界、格式化字符串、竞态条件。

## 0. 一个统一的观察角度

上一篇讲了内存管理的机制：每一段虚拟地址对应某个页帧，有明确的权限（读/写/执行）。这些机制背后有一组**不变量**，程序与编译器都默认它们成立：

| 不变量 | 内容 | 被破坏后的后果 |
| --- | --- | --- |
| 边界不变量 | 对缓冲区的第 i 次写入只会落在 `[0, len)` 内 | 越界写覆盖相邻数据 |
| 生命周期不变量 | 指针在存活期内始终指向有效对象 | use-after-free |
| 所有权不变量 | 一块内存只被释放一次 | double free |
| 类型不变量 | 数据的解释方式与其实际布局一致 | 格式化字符串、类型混淆 |
| 别名不变量 | 不存在意外的重叠引用 | 数据竞争、TOCTOU |
| 算术不变量 | 长度计算不会回绕 | 分配过小 + 越界写 |

**几乎所有内存类漏洞都是某一个不变量被破坏的结果。** 后面的每一节，都可以归纳为"哪个不变量、被什么行为破坏、破坏后能得到什么"。

> 本笔记只讲原理与不变量，不针对任何具体漏洞编号。这里不会出现 CVE 编号，需要联系真实案例请自行到 NVD（National Vulnerability Database）或厂商安全公告检索。

## 1. 缓冲区溢出 (buffer overflow)

### 1.1 栈缓冲区溢出 (stack buffer overflow)

典型的 C 代码：

```c
#include <string.h>

void vulnerable(const char *input) {
    char buf[64];
    strcpy(buf, input);   /* 不检查长度 */
    printf("%s\n", buf);
}
```

`strcpy` 把 `input` 完整复制到 64 字节的 `buf`，只要输入长度超过 63（加结尾 `\0`），多出的字节就按**地址递增方向**写到 `buf` 之后的内存里。

在典型的 x86-64 栈布局中（栈向低地址增长，因此数组溢出向高地址写）：

```text
        高地址
    +---------------------------+
    |  调用者的栈帧 / 参数区域   |
    +---------------------------+
    |  保存的返回地址 (return    |  <-- 溢出到这里的第一个"有价值目标"
    |  address, 8 字节)          |
    +---------------------------+
    |  保存的 RBP (saved rbp)    |
    +---------------------------+
    |  局部变量 / canary         |  <-- 栈保护在这里放哨
    +---------------------------+
    |  char buf[64]              |  <-- 溢出的起点
    +---------------------------+
        低地址
```

被破坏的第一个关键目标是**保存的返回地址**。函数返回时 `ret` 指令从栈上弹出该地址并跳转，于是控制流被输入数据掌握。这就是栈溢出的根本危害：**用数据覆盖了控制流**。

几个必须澄清的细节：

- **写入方向取决于数组的生长方向**，不是"栈溢出一定覆盖返回地址"。全局数组溢出会覆盖相邻全局变量，堆上数组溢出覆盖堆元数据。
- **越界读**（如 `memcpy(dst, src, len)` 中 `len` 过大导致读越界）同样严重，会造成信息泄露 (information disclosure)，是绕过 ASLR 的常用手段。
- **off-by-one** 是溢出的一种特例：多写/少写一个字节。一个字节就足以破坏相邻变量的最低有效字节，或破坏栈上保存的指针/长度字段。

造成溢出的常见 API（这些是真实存在的标准函数）：

| 危险函数 | 问题 | 安全替代 |
| --- | --- | --- |
| `strcpy` / `strcat` | 无长度参数 | `strncpy` / `strncat`（注意 `strncpy` 可能不写结尾 `\0`），或 `snprintf` |
| `sprintf` / `vsprintf` | 无长度参数 | `snprintf` / `vsnprintf` |
| `gets` | 完全无法限制长度 | 已从 C11 标准中移除，用 `fgets` |
| `memcpy` / `memmove` | 长度由调用者负责，长度算错就溢出 | 调用前校验长度上界 |
| `scanf("%s")` | 无宽度限制 | `scanf("%63s", buf)` 明确指定宽度 |

### 1.2 堆缓冲区溢出 (heap buffer overflow)

```c
char *p = malloc(64);
strcpy(p, input);   /* input 长度超过 64 */
```

堆上溢出不覆盖返回地址（堆与栈不在同一区域），它破坏的是**相邻堆块的元数据或其他对象**。传统 `glibc` malloc 的块结构大致如下：

```text
    +-------------------+-------------------+-------------------+-------------------+
    | 前一块的 size      | 本块 size+flags    |  用户数据 ...      | 下一块的 header    |
    +-------------------+-------------------+-------------------+-------------------+
      prev_size            size (低 3 位为标志位)   <-- 溢出从这里写出去
```

`size` 字段的最低几位是标志位（`PREV_INUSE` 等），因此**写越界哪怕只改掉一个字节，也可能伪造出"前一块空闲"的假象**，进而让 `free()` 在合并空闲块时把攻击者控制的地址写进空闲链表。这就是堆溢出的经典利用路径：不直接劫持控制流，而是污染分配器的元数据，等待程序自己"踩上去"。

堆溢出的两种典型位置：

- **溢出到下一个 chunk 的元数据**（如上）；
- **溢出到下一个对象**（例如两个 C++ 对象相邻分配，溢出改写后者的虚表指针 vptr，从而在调用虚函数时劫持控制流）。

### 1.3 破坏的是哪个不变量

> **边界不变量**：写入位置必须落在缓冲区长度之内。溢出的本质是"长度信息"与"实际写入长度"不一致。

## 2. Use-after-free (UAF)

概念：**释放一块内存后仍然通过旧指针访问它**。

```c
struct Session *s = malloc(sizeof(struct Session));
s->is_admin = 0;
/* ... 使用 s ... */
free(s);
/* ... 别的代码申请了同样大小的对象 ... */
struct Session *evil = malloc(sizeof(struct Session));  /* 很可能拿到同一块内存 */
evil->is_admin = 1;
/* 此时通过过期的 s 访问 */
if (s->is_admin) {          /* 读到的其实是 evil 写入的数据 */
    grant_admin();
}
```

关键机制：`free()` **不会清零内存**，通常只是把块放回空闲链表。之后同尺寸的 `malloc()` 极有可能返回同一个地址（空闲链表是 LIFO 的，这使复用几乎是必然的）。于是：

- **读**过期指针 → 读到后来者写入的数据（信息泄露）；
- **写**过期指针 → 篡改后来者的数据（数据完整性破坏，乃至控制流劫持，例如对象里含函数指针或 vptr）。

UAF 的两种变体：

- **悬垂指针 (dangling pointer)**：如上，指针本身还在用。
- **双重引用 (aliasing)**：两个不同生命周期的对象共享同一块内存，一方释放后另一方仍认为它有效。这在手动内存管理的语言里很常见，也是智能指针/所有权模型要解决的问题。

UAF 常与**堆喷 (heap spraying)** 配合：攻击者先制造大量同尺寸分配，让释放后的槽位大概率被自己控制的数据填充，从而提高利用的稳定性。

> 破坏的不变量：**生命周期不变量**。指针的有效性没有被任何机制跟踪——`free` 无法知道还有多少个指针指向这块内存。

## 3. Double free

概念：**对同一块内存调用两次 `free()`**。

```c
char *p = malloc(128);
free(p);
free(p);        /* 未定义行为 */
```

后果链条：

1. 第二次 `free` 把同一个 chunk 再次插入空闲链表；
2. 于是**同一个地址在空闲链表里出现两次**（或者空闲链表出现自环）；
3. 接下来两次 `malloc` 会返回**同一个地址**，程序里出现两个"合法"对象指向同一块内存；
4. 这就是一个受控的别名 (aliasing) 问题，攻击者可以让两个逻辑上独立的对象互相影响，最终写出任意值。

现代分配器（`glibc` 2.29 起引入了对 chunk 内存中关键字段的检查，即所谓的 tcache double-free 检测）会检测一部分 double free 并中止程序，但**检测是不完整的**，仍存在绕过方式。因此 double free 的正确防线是编程规范与工具（见 `03-defense-strategies.md`），不是分配器的检测。

常见的"意外 double free"写法：

```c
/* 反例 1: 释放后没有置空，之后错误路径再次释放 */
free(p);
/* ... 中间有很长的逻辑 ... */
if (error) {
    free(p);      /* 忘了 p 已经被释放/或者本该置为 NULL */
}

/* 反例 2: 两个结构共享一个指针，各自的析构函数都去释放它 */
```

一个广泛使用的缓解习惯是**释放后立即置空**：

```c
free(p);
p = NULL;
```

这样第二次 `free(NULL)` 是良定义的空操作。但它**只对单个指针变量有效**，如果存在多个指向同一对象的指针，置空一个不影响其他的，因此它缓解的是"同一个变量被释放两次"，不是"同一块内存被释放两次"。这一点必须区分清楚，否则会给人虚假的安全感。

> 破坏的不变量：**所有权不变量**。"谁负责释放"必须唯一，而 C 的 `free` 无法验证这个前提。

## 4. 整数溢出导致的越界 (integer overflow → out-of-bounds)

这类漏洞的特点是：**边界检查写在了，但检查用的算术本身就是错的**。

### 4.1 典型的长度计算回绕

```c
/* 设想：分配 header + payload 的空间 */
size_t total = sizeof(struct Header) + user_len;   /* 无符号运算 */
char *buf = malloc(total);
if (buf == NULL) return -1;
memcpy(buf + sizeof(struct Header), user_data, user_len);
```

如果 `user_len` 非常接近 `SIZE_MAX`，`sizeof(struct Header) + user_len` 会**回绕 (wrap around)** 成一个很小的值。于是 `malloc` 只分配了一个小缓冲区，而 `memcpy` 仍然按原始的、巨大的 `user_len` 去写 —— 一次彻底失控的堆溢出。

同理还有乘法版本：

```c
size_t bytes = count * elem_size;    /* count 与 elem_size 都是无符号 */
char *p = malloc(bytes);             /* count 很大时 bytes 回绕变小 */
for (size_t i = 0; i < count; i++) {
    p[i] = ...;                      /* 按原始 count 循环 → 越界写 */
}
```

### 4.2 有符号溢出与类型转换

- **有符号溢出在 C 中是未定义行为 (undefined behavior)**，编译器可以假定它不发生，因此基于"溢出后判断符号位"的检查可能被优化掉。
- **有符号 ↔ 无符号转换**是另一个陷阱：把一个负数 `int` 赋给 `size_t` 会变成一个巨大的正数，这就是上面回绕的入口。
- **窄化转换 (truncation)**：把 64 位长度截断成 32 位后再使用，高位信息丢失。

### 4.3 比较时的符号问题

```c
int len = read_from_network(buf, sizeof(buf));   /* 出错返回 -1 */
if (len < sizeof(buf)) {                         /* sizeof 是 size_t（无符号） */
    /* 由于 -1 会被转换成巨大的无符号数，这个条件实际上把错误码也放行了 */
    memcpy(dest, buf, len);                      /* len == -1 → 巨大长度 → 灾难 */
}
```

这里 `len < sizeof(buf)` 的比较会触发**整型提升 (usual arithmetic conversions)**，`len` 被转换为 `size_t`。这是一个非常经典的"检查形同虚设"的例子。

### 4.4 正确的检查方式

原则是：**在运算之前检查，而不是之后**。

```c
/* 加法检查 */
if (user_len > SIZE_MAX - sizeof(struct Header)) {
    return -EINVAL;                 /* 拒绝，而不是先算后查 */
}
size_t total = sizeof(struct Header) + user_len;

/* 乘法检查 */
if (count != 0 && elem_size > SIZE_MAX / count) {
    return -EINVAL;
}
size_t bytes = count * elem_size;
```

或者使用编译器内建函数（GCC / Clang 都提供，但属于扩展而非标准 C）：

```c
size_t total;
if (__builtin_add_overflow(sizeof(struct Header), user_len, &total)) {
    return -EINVAL;
}
```

另外，对"来自外部的长度"应当设一个**业务上的合理上界**（例如"单个消息不超过 1 MiB"），这比追逐所有算术边界更可靠，也更容易审计。

> 破坏的不变量：**算术不变量**。边界检查依赖于长度计算的正确性，而长度计算本身溢出了。

## 5. 格式化字符串漏洞 (format string vulnerability)

成因：**把用户数据当作格式串 (format string) 传给了 `printf` 家族函数**。

```c
/* 脆弱写法 */
printf(user_input);

/* 正确写法 */
printf("%s", user_input);
```

为什么危险？因为格式串不是"普通字符串"，它是**一份对调用约定的指令**：`%s` 告诉 `printf` "从下一个参数槽取一个指针并解引用它"，`%n` 告诉它"把已输出的字符数**写入**下一个参数槽指向的地址"。当格式串来自用户，用户就获得了对参数列表的解释权。

### 5.1 信息泄露（读取）

栈上的可变参数区域紧邻局部变量，`printf` 会因为找不到真正对应的参数而**继续往栈上读**：

```text
printf("%p %p %p %p %p\n", ...);   /* 不需要提供参数，直接打印栈上的值 */
printf("%s", ...);                 /* 把栈上的某个值当地址解引用 → 可能读到内存内容 */
```

这可以泄露栈上的数据、保存的指针，从而击穿 ASLR（见 `03-defense-strategies.md` 第 1 节）。

### 5.2 内存写入（`%n`）

`%n` 把已输出字符数写到指定地址，配合**宽度修饰**可以精确控制写入的值：

```text
%100c%n    -> 输出 100 个字符，然后把 100 写入目标地址
%hhn       -> 只写 1 个字节（便于逐字节构造任意值）
```

配合栈上可控的参数（例如攻击者的输入本身就位于栈上），就可以把任意值写到任意地址。**因此格式化字符串漏洞的完整危害是任意地址写 (arbitrary write)**，这一点比"能打印内存"严重得多。

### 5.3 编译期防护

现代编译器会对**字面量**格式串与参数类型做检查：

```bash
gcc -Wall -Wformat -Wformat-security -Werror=format-security -o app app.c
```

但这对 `printf(user_input)` 这种"格式串是变量"的写法，作用有限（`-Wformat-security` 会在格式串非字面量且无参数时给出警告，这是目前最有效的静态信号）。

> 破坏的不变量：**类型不变量**。格式串声明了参数类型，而实际参数与之不匹配，调用约定被违反且没有任何运行时检查。

## 6. 竞态条件 (race condition)

概念：**多个执行流对共享状态的访问顺序会影响结果，而代码没有做同步**。

### 6.1 数据竞争 (data race)

```c
/* 两个线程同时执行 */
counter++;      /* 实际是 read-modify-write 三步，不是原子操作 */
```

不加锁的情况下，两个线程可能读到相同的旧值，各自加一后写回，最终结果是 1 而非 2（丢失更新, lost update）。C/C++ 中**未同步的并发读写同一内存位置是未定义行为**，不只是"结果可能不对"。

### 6.2 TOCTOU (Time-of-Check to Time-of-Use)

这是与文件/权限相关的经典竞态，模式是：**检查 (check) 与使用 (use) 之间存在时间窗口，攻击者可以在窗口内改变状态**。

```c
/* 脆弱模式 */
if (access("/tmp/userfile", W_OK) == 0) {      /* 检查时刻 */
    /* ... 攻击者在这里把 /tmp/userfile 换成指向 /etc/shadow 的符号链接 ... */
    fd = open("/tmp/userfile", O_WRONLY);      /* 使用时刻：路径已被替换 */
    write(fd, data, len);                      /* 写到了错误的目标 */
}
```

为什么这里"检查"没有意义：`access()` 检查的是**当时那个路径名**指向的对象，而 `open()` 会重新解析路径名。两次解析之间，路径的指向可以被改变（符号链接是主要原因之一）。

**正确的思路是消除"名字→对象"的二次解析**，用一个原子操作替代"先检查后使用"：

```c
/* 用 O_NOFOLLOW 拒绝符号链接，并直接用打开后的 fd 操作，不再依赖路径名 */
fd = open("/tmp/userfile", O_WRONLY | O_NOFOLLOW | O_CREAT, 0600);
if (fd < 0) { /* 处理错误，而不是回退到"先检查" */ }

/* 更严格的做法：打开目录 fd 后用 openat / fstatat 配合 AT_SYMLINK_NOFOLLOW，
   所有后续操作都基于 fd 而不是路径名 */
```

用 `fstat()` 检查已经打开的描述符，而不是用 `stat()` 检查路径名 —— 这是"基于 fd (fd-based)"的安全编程核心。

### 6.3 其他常见的共享状态问题

| 问题 | 说明 |
| --- | --- |
| 令牌/权限缓存不一致 | 权限被撤销后，缓存中的旧权限仍然生效一段时间 |
| 惰性初始化竞态 | 两个线程同时发现"未初始化"，各自初始化一次，导致双重初始化或内存泄漏 |
| 信号处理函数中的不安全操作 | 信号处理函数里调用非 async-signal-safe 函数（如 `printf`、`malloc`）会与主流程交错，产生难以复现的破坏 |
| 临时文件竞态 | 用可预测的文件名（如 `/tmp/app.tmp`）配合 `O_CREAT` 而不加 `O_EXCL`，多个实例互相覆盖 |

> 破坏的不变量：**别名/顺序不变量**。单线程推理下的"这两个操作之间有先后关系"假设，在并发下不再成立。

## 7. 一张总表：漏洞类型 → 破坏的不变量 → 危害 → 典型触发点

| 漏洞类型 | 破坏的不变量 | 直接危害 | 典型触发点 |
| --- | --- | --- | --- |
| 栈缓冲区溢出 | 边界 | 覆盖返回地址，劫持控制流 | `strcpy` / `sprintf` / `gets` / 手写循环 |
| 堆缓冲区溢出 | 边界 | 污染分配器元数据或相邻对象 | `memcpy` 长度算错 / `strcpy` 无界 |
| Use-after-free | 生命周期 | 读写他人对象，控制流劫持 | `free` 后指针未置空、生命周期管理混乱 |
| Double free | 所有权 | 空闲链表出现重复项，制造别名 | 错误路径重复释放、共享所有权 |
| 整数溢出 → 越界 | 算术 | 小分配 + 大写入 | 长度加法/乘法回绕、有符号无符号混用 |
| 格式化字符串 | 类型 | 信息泄露、任意地址写 | `printf(user_input)`、日志封装函数 |
| 竞态条件 / TOCTOU | 别名与顺序 | 状态被绕过，权限检查失效 | 路径名二次解析、未加锁的共享变量 |

## 8. 一个通用的分析流程

拿到一段可疑代码时，我用的检查顺序是（这个顺序在下一篇的案例分析框架里还会复用）：

```text
1. 列出所有来自外部的输入（网络、文件、命令行、环境变量、IPC）
2. 找出所有"长度/索引/偏移量"，逐个问：它的上界在哪里被验证？
   - 验证发生在运算之前还是之后？
   - 是有符号还是无符号？会不会回绕或截断？
3. 找出所有内存的"生命周期"：谁分配、谁释放、释放后还有谁持有指针？
4. 找出所有"检查与使用"成对出现的代码：中间有没有可以改变状态的窗口？
5. 找出所有把数据当代码/格式/类型解释的地方：格式串、反序列化、类型转换
6. 对每一处，写下"假设成立时需要什么条件"，再问运行时是否真的保证了这个条件
   —— 第 6 步是下一篇《配置校验与运行时执行之间的脱节》的核心。
```

## 小结

- 内存类漏洞可以统一表述为"某个不变量被破坏"，这比按 CVE 逐个记忆更适合建立体系。
- 溢出的本质是长度信息与实际写入长度不一致；栈溢出的目标是返回地址，堆溢出的目标是分配器元数据或相邻对象。
- `free` 不清零、不清空指针，因此 UAF 与 double free 的根源是**生命周期与所有权没有语言级保证**；"释放后置空"只能缓解单变量重复释放。
- 整数溢出类漏洞的可怕之处在于**边界检查本身被算术回绕骗过**，所以检查必须在运算前做，并且要对外部长度设业务上界。
- 格式化字符串把用户数据变成"调用约定的指令"，`%n` 使它成为任意地址写。
- 竞态条件的正解不是"检查得更仔细"，而是**消除检查与使用之间的时间窗口**（例如改用基于 fd 的操作）。
