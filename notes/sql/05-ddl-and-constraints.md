# 数据定义与约束：CREATE TABLE、主外键、索引基础

本篇梳理 SQL 的数据类型选型、`CREATE TABLE` 与六类约束的语义、`ALTER TABLE` 的风险，以及索引的工作原理与"什么时候用不上索引"。

## 0. DDL 的范围与一个重要的特性

```sql
-- DDL：定义/修改结构
CREATE TABLE ...        -- 建表
ALTER  TABLE ...        -- 改表结构
DROP   TABLE ...        -- 删表
CREATE INDEX ...        -- 建索引
CREATE VIEW ...         -- 建视图
TRUNCATE TABLE ...      -- 清空表（保留结构）

-- 与之对照的 DML：操作数据
INSERT / UPDATE / DELETE / SELECT
```

**DDL 的一个关键特性：很多数据库对 DDL 做隐式提交 (implicit commit)。**

```sql
BEGIN;
CREATE TABLE t (id INT);
ROLLBACK;                 -- ⚠️ 在 MySQL 里，表 t 不会被回滚掉！因为 CREATE TABLE 已经隐式提交了事务
```

| 数据库 | DDL 能否在事务中回滚 |
| --- | --- |
| MySQL | ❌ **不能**（DDL 导致隐式提交） |
| Oracle | ❌ 不能（同样隐式提交） |
| **PostgreSQL** | ✅ **能**（PostgreSQL 支持事务性 DDL，`BEGIN; CREATE TABLE ...; ROLLBACK;` 会真的回滚） |
| SQLite | ✅ 能（大部分 DDL 是事务性的） |

**这个差异很实用**：在 PostgreSQL 上改表结构时可以先 `BEGIN`，验证通过再 `COMMIT`，出错就 `ROLLBACK`；而在 MySQL 上**没有后悔药**（所以生产环境改表前必须备份）。

## 1. 数据类型

### 1.1 整数

| 类型 | 典型范围 | 用途 |
| --- | --- | --- |
| `SMALLINT` | 16 位有符号（约 ±3.2 万） | 小范围的计数、状态码 |
| `INTEGER` / `INT` | 32 位有符号（约 ±21 亿） | **默认选择** |
| `BIGINT` | 64 位有符号 | 可能超过 21 亿的 ID、累计计数、时间戳（微秒） |

**关于自增类型**（这个各家写法差别很大，值得单独记）：

| 数据库 | 自增主键的写法 |
| --- | --- |
| MySQL | `INT AUTO_INCREMENT PRIMARY KEY` |
| PostgreSQL (旧式) | `SERIAL` / `BIGSERIAL`（本质是创建一个序列并设为默认值） |
| PostgreSQL (标准) | `INTEGER GENERATED ALWAYS AS IDENTITY` / `GENERATED BY DEFAULT AS IDENTITY` |
| SQLite | `INTEGER PRIMARY KEY AUTOINCREMENT`（甚至只写 `INTEGER PRIMARY KEY` 就有 rowid 自增行为） |
| SQL Server | `INT IDENTITY(1,1)` |
| Oracle (12c+) | `NUMBER GENERATED BY DEFAULT AS IDENTITY` |

**标准 SQL 推荐 `GENERATED ... AS IDENTITY`**，它把"自增"作为列定义的一部分，避免了 `SERIAL` 那种"隐式创建序列、列与序列可能失配"的问题。但 `SERIAL` 在 PostgreSQL 生态里用得非常普遍，读旧代码时一定会遇到。

**`AUTOINCREMENT` 在 SQLite 里的一个细节**：SQLite 的 `INTEGER PRIMARY KEY` 本身就是 rowid 的别名，会自动分配比当前最大值大的值；而加了 `AUTOINCREMENT` 关键字会额外保证"不复用已删除的 ID"（代价是维护一个 `sqlite_sequence` 表）。**所以 SQLite 里 `AUTOINCREMENT` 不是必需的**，只有在"ID 不能被复用"这个需求下才需要。

> ⚠️ **关于整数溢出的现实风险**：用 `INT` 做 ID 时，如果数据量可能超过 21 亿（例如高流量的日志表、事件表），必须用 `BIGINT`。**把 `INT` 主键改成 `BIGINT` 在大表上是一个代价很高的操作**（可能锁表很久），所以**建表时就该想清楚**。这是一个经典的"事后修改成本极高"的决定。

### 1.2 定点数与浮点数 —— 这是一个容易造成真实损失的坑

| 类型 | 精度 | 用途 |
| --- | --- | --- |
| `NUMERIC(p, s)` / `DECIMAL(p, s)` | **精确 (exact)** | **金额、分数、任何不能有舍入误差的数据** |
| `REAL` / `FLOAT` | 近似 (approximate) | 科学计算、传感器读数、需要节省空间的大批量测量值 |
| `DOUBLE PRECISION` | 近似，双精度 | 同上，精度更高 |

`NUMERIC(p, s)` 里 `p` 是**总位数 (precision)**，`s` 是**小数位数 (scale)**：

```sql
NUMERIC(5, 2)     -- 总共 5 位，其中 2 位小数 → 范围 -999.99 到 999.99（正好适合 100 分制成绩）
NUMERIC(10, 2)    -- 适合金额，最大 99999999.99
NUMERIC(12, 4)    -- 适合需要 4 位小数的比率
NUMERIC           -- 不指定精度时通常是"任意精度"（各数据库行为略有不同）
```

**为什么不能用 `FLOAT` 存金额**：`FLOAT` / `DOUBLE` 用**二进制**表示小数，而很多十进制小数（如 `0.1`、`0.2`）在二进制下是**无限循环小数**，只能近似存储。所以：

```text
在 IEEE 754 双精度下：
    0.1 + 0.2 的结果不是 0.3，而是 0.30000000000000004
```

这不是数据库的 bug，而是**二进制浮点的固有性质**。后果：

```sql
-- ❌ 用 FLOAT 存金额
CREATE TABLE payments_float (
    id     INTEGER PRIMARY KEY,
    amount DOUBLE PRECISION
);
-- 累加 100 笔 0.1 元时，总和可能不是 10.00，而是 9.99999999999998
-- 对账时就会出现"差 1 分钱"的诡异问题

-- ✅ 用 NUMERIC 存金额
CREATE TABLE payments (
    id     INTEGER PRIMARY KEY,
    amount NUMERIC(10, 2) NOT NULL
);
-- 精确，累加 100 笔 0.1 就是 10.00
```

**结论：只要涉及"钱"或"必须精确对账的数字"，一律用 `NUMERIC` / `DECIMAL`。** 这是本篇最实用的一条建议。

**顺带说一个相关的实践**：也有些系统干脆**用整数存"最小货币单位"**（例如用"分"存金额，`12345` 表示 123.45 元）。这样完全避开小数问题，代价是显示层要做换算。两种做法都常见。

### 1.3 字符串

| 类型 | 特点 | 建议 |
| --- | --- | --- |
| `CHAR(n)` | **定长**，不足会补空格 | 只在长度严格固定时用（如 `CHAR(1)` 存性别、`CHAR(2)` 存国家代码） |
| `VARCHAR(n)` | **变长**，最多 n 个字符 | **默认选择** |
| `TEXT` | 变长，通常无长度上限（或上限很大） | 长文本、备注、JSON 内容 |

**`CHAR` 的补空格行为会咬人**：

```sql
CREATE TABLE t (code CHAR(5));
INSERT INTO t VALUES ('ab');
SELECT '[' || code || ']' FROM t;    -- 输出 [ab   ] —— 注意补了 3 个空格！
SELECT LENGTH(code) FROM t;          -- 在多数数据库上返回 5（含补的空格）
```

在比较时通常会自动忽略尾部空格（这取决于数据库与 `PAD SPACE` / `NO PAD` 排序规则），但这会造成"看起来相等但不相等"的困惑。**结论：除非长度严格固定，用 `VARCHAR`。**

**关于 `VARCHAR(n)` 里 `n` 的含义**：

| 数据库 | `VARCHAR(n)` 的 `n` 是 |
| --- | --- |
| 标准 SQL / PostgreSQL / SQLite | **字符数** |
| MySQL | **字符数**（不是字节数！`VARCHAR(50)` 在 `utf8mb4` 下能存 50 个字符，最多占 200 字节） |
| Oracle | 默认是**字节数**（`VARCHAR2(50 BYTE)`），要按字符算需写 `VARCHAR2(50 CHAR)` |
| SQL Server | `VARCHAR(n)` 是**字节数**（单字节编码），`NVARCHAR(n)` 是字符数 |

**这一点必须按数据库确认**，因为它直接影响"能存多长的中文/emoji"。MySQL 的 `utf8mb4` 是推荐的字符集（真正的 4 字节 UTF-8，能存 emoji；旧的 `utf8` 在 MySQL 里其实是 3 字节的限制版，存 emoji 会失败或截断）。

**一个实践建议**：`VARCHAR(n)` 里的 `n` 不要无脑写很大（例如 `VARCHAR(255)` 或 `VARCHAR(4000)`）。虽然多数数据库对 `VARCHAR` 是按实际内容存储的，但：

- 某些数据库会基于声明的长度做内存预留或排序策略选择；
- 索引对列长度可能有限制（MySQL 的索引键长度有上限，过长的 `VARCHAR` 做索引会失败）；
- 声明一个合理的上限本身就是一层**数据校验**（防止误写入超长内容）。

**`VARCHAR` 与 `TEXT` 的选择**：`TEXT` 更灵活，但很多数据库对 `TEXT` 列有一些限制（不能直接建索引、不能有默认值、排序行为不同）。**如果长度可以预估，用 `VARCHAR(n)`；确实是不定长的大文本才用 `TEXT`。**

### 1.4 日期与时间

| 类型 | 含义 | 时区 |
| --- | --- | --- |
| `DATE` | 只有日期（年月日） | 无 |
| `TIME` | 只有时间 | 无 |
| `TIMESTAMP` | 日期 + 时间 | **取决于数据库**（见下） |
| `TIMESTAMP WITH TIME ZONE` / `TIMESTAMPTZ` | 带时区信息的时间点 | 有 |
| `DATETIME`（MySQL） | 日期 + 时间 | **无时区**，存什么就是什么 |
| `INTERVAL` | 时间间隔 | — |

**时区问题需要按数据库区分**：

| 数据库 | `TIMESTAMP` 的时区行为 |
| --- | --- |
| PostgreSQL | `TIMESTAMP` **不带**时区；`TIMESTAMPTZ` 是 `TIMESTAMP WITH TIME ZONE`，内部存 UTC，按会话时区显示 |
| MySQL | `TIMESTAMP` **受 `time_zone` 影响**（写入时转换为 UTC 存储，读取时转回会话时区）；`DATETIME` **不受时区影响** |
| SQLite | 没有原生日期时间类型，存字符串或数字，一切靠约定 |
| SQL Server | `DATETIME`/`DATETIME2` 不带时区；`DATETIMEOFFSET` 带 |

**关于 `TIMESTAMP` 的 2038 问题**：MySQL 的 `TIMESTAMP` 是 32 位 Unix 时间戳，**有一个上限（2038-01-19 03:14:07 UTC）**，超过就无法表示。这是一个众所周知的事实（与 32 位系统的 `time_t` 同源）。**这也是 MySQL 里更推荐用 `DATETIME` 存"业务上不需要时区转换的时间"的原因之一**——`DATETIME` 的范围大得多。

**推荐的实践**：

1. **存 UTC**：所有时间戳以 UTC 存储，显示时按用户时区转换。这样跨时区不会错乱，也不会因为夏令时切换出问题。
2. **或者在需要"本地墙上时间"时用不带时区的类型**：例如"店铺每天 9:00 开门"这个 9:00 是**本地墙钟时间**，不该随时区变。这类场景用不带时区的类型是正确的。
3. **两者不要混用**：一个系统里有些时间带时区、有些不带，是最容易出错的状态。**在建表时就明确约定。**
4. **时间范围查询用左闭右开**（见 [01-basic-query.md](01-basic-query.md) 第 4.3 节），避免漏掉最后一天。

### 1.5 布尔

| 数据库 | 布尔表示 |
| --- | --- |
| 标准 SQL | `BOOLEAN` |
| PostgreSQL | `BOOLEAN`，值为 `TRUE` / `FALSE` / `NULL`（也接受 `'t'`/`'f'`、`'yes'`/`'no'` 等输入形式） |
| MySQL | `BOOLEAN` / `BOOL` **是 `TINYINT(1)` 的同义词**，存 0/1（可以存其他整数，不严格） |
| SQLite | **没有布尔类型**，用整数 0/1 存（`TRUE`/`FALSE` 关键字从 3.23 起被识别为 1/0） |
| SQL Server | `BIT` |

**注意 MySQL 的 `BOOLEAN` 只是别名**，所以 `WHERE is_active = TRUE` 实际上在和 1 比较，而如果一个应用往里写了 `2`，条件就不成立了。这是"MySQL 的布尔不严格"这个真实问题的来源。

**关于 `NULL`**：`NULL` **不是一种类型**，而是"这一列是否可空"的**可空性 (nullability)** 属性。任何类型都可以是 `NULL`，除非明确加了 `NOT NULL`。

### 1.6 类型选型速查

| 要存什么 | 用什么 |
| --- | --- |
| ID | `BIGINT`（有余量）或 `INTEGER`；自增按数据库方言写 |
| 金额 | **`NUMERIC(12,2)`**（绝对不要 `FLOAT`/`DOUBLE`） |
| 成绩（100 分制，允许 2 位小数） | `NUMERIC(5,2)` |
| 比率 / 百分比 | `NUMERIC(5,2)`（0.00 到 100.00）或 `NUMERIC(9,6)` |
| 姓名 / 城市 / 标题 | `VARCHAR(n)`，`n` 按业务合理上限 |
| 固定长度的编码 | `CHAR(n)` |
| 长文本 / 备注 / JSON 文本 | `TEXT`（PostgreSQL 还有专门的 `JSONB`） |
| 时间戳 | 存 UTC → `TIMESTAMPTZ`（PostgreSQL）/ `TIMESTAMP`（MySQL，注意 2038）；本地墙钟 → `DATETIME`（MySQL）/ `TIMESTAMP`（PostgreSQL） |
| 只要日期 | `DATE` |
| 是/否 | `BOOLEAN`（注意 MySQL 里是 `TINYINT(1)` 的别名） |
| 枚举 | `VARCHAR` + `CHECK` 约束（可移植），或数据库特有的 `ENUM` 类型（MySQL，但不便修改） |

## 2. `CREATE TABLE` 语法

```sql
CREATE TABLE [IF NOT EXISTS] table_name (
    column_name  data_type  [column_constraint ...],
    ...
    [table_constraint ...]
);
```

### 2.1 列级约束与表级约束

```sql
CREATE TABLE enrollments (
    -- 列级约束：直接写在列定义后面
    enrollment_id INTEGER      PRIMARY KEY,
    student_id    INTEGER      NOT NULL,
    course_id     INTEGER      NOT NULL,
    score         NUMERIC(5,2) CHECK (score >= 0 AND score <= 100),
    semester      VARCHAR(20)  NOT NULL DEFAULT '2025-Spring',

    -- 表级约束：可以涉及多列（复合键、复合唯一）
    CONSTRAINT fk_enroll_student FOREIGN KEY (student_id) REFERENCES students (student_id),
    CONSTRAINT fk_enroll_course  FOREIGN KEY (course_id)  REFERENCES courses (course_id),
    CONSTRAINT uq_enroll         UNIQUE (student_id, course_id, semester)
);
```

| | 列级约束 | 表级约束 |
| --- | --- | --- |
| 位置 | 紧跟列定义 | 在列定义之后 |
| 涉及多列 | ❌ 不能 | ✅ 可以 |
| 命名 | 通常省略（系统自动生成名字） | 通常显式命名 |
| 何时必须用表级 | — | 复合主键、复合唯一、复合外键 |

**`CONSTRAINT <名字> ...` 的价值**：显式命名后，后续要删除或修改约束就有明确的名字可引用：

```sql
-- 有名字，可以精确删除
ALTER TABLE enrollments DROP CONSTRAINT uq_enroll;

-- 没有名字的话，得先去查系统目录找出系统生成的名字，很麻烦
```

**关于 `IF NOT EXISTS`**：MySQL、PostgreSQL、SQLite 支持 `CREATE TABLE IF NOT EXISTS`；**Oracle 不支持**（Oracle 需要靠 PL/SQL 块判断）。所以"多数数据库支持，但不是所有"——写跨数据库的迁移脚本时要确认。

## 3. 六类约束

### 3.1 `NOT NULL`

```sql
CREATE TABLE students (
    student_id INTEGER PRIMARY KEY,
    name       VARCHAR(50) NOT NULL,      -- 必须有值
    major      VARCHAR(50)                -- 可空
);
```

`NOT NULL` 是**列的基础属性**，不是可以在表级定义的约束（表级不能写 `NOT NULL`，因为它天然只涉及一列）。

**一个重要的设计原则**：**尽量加 `NOT NULL`，并用 `DEFAULT` 提供默认值。** 理由：

- 可空列是 `NULL` 陷阱的主要来源（见 [01-basic-query.md](01-basic-query.md) 的三值逻辑）；
- 应用代码里每个可空列都要处理 `null` 分支，很容易漏；
- 但如果列**业务上确实可能"未知"**，那 `NOT NULL` 加一个假默认值（如空字符串、0）反而**丢失了"未知"这个语义**。这时候正确的做法是保留可空，并在应用层明确处理。

```sql
-- ❌ 为了 NOT NULL 而给出误导性的默认值
email VARCHAR(100) NOT NULL DEFAULT ''      -- 空字符串到底是"没有邮箱"还是"没填"？
-- 这时 `WHERE email = ''` 和"没填"分不清，与 NULL 的语义混淆了

-- ✅ 要么允许 NULL（明确表示"未知/未填"）
email VARCHAR(100)

-- ✅ 要么用 NOT NULL 但配合明确的默认值（业务上确实有默认）
enroll_year INTEGER NOT NULL DEFAULT 2025
```

### 3.2 `DEFAULT`（含一个常见误解）

```sql
CREATE TABLE t (
    id         INTEGER PRIMARY KEY,
    status     VARCHAR(20)  NOT NULL DEFAULT 'pending',
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    is_active  BOOLEAN      NOT NULL DEFAULT TRUE,
    retry      INTEGER      NOT NULL DEFAULT 0,
    remark     VARCHAR(100) DEFAULT NULL
);
```

> ⚠️ **`DEFAULT` 只在 INSERT 时"省略该列"才生效。显式写入 `NULL` 不会触发默认值。**

```sql
INSERT INTO t (id, status) VALUES (1, 'done');
-- status = 'done'；created_at 使用默认值 CURRENT_TIMESTAMP；其他列用各自的默认值

-- ❌ 显式写 NULL 会【覆盖】默认值（如果列允许 NULL）
INSERT INTO t (id, status, retry) VALUES (2, 'done', NULL);
-- retry = NULL，不是 0！DEFAULT 不生效

-- ✅ 要用默认值就省略该列，或者显式写 DEFAULT 关键字
INSERT INTO t (id, status, retry) VALUES (3, 'done', DEFAULT);
-- 用 DEFAULT 关键字明确要求"用默认值"（标准 SQL 写法，主流数据库支持）

-- ✅ 也可以用 COALESCE 在应用层处理
INSERT INTO t (id, status, retry) VALUES (4, 'done', COALESCE(:retry, 0));
```

**这个误解很常见**：以为"传入 `NULL` 就会变成默认值"。**实际上 `DEFAULT` 是"列缺失时"的填充值，不是"值为 NULL 时"的替换值。** 要在写入时让 NULL 变默认值，必须在应用层做（`COALESCE`），或者给列加 `NOT NULL` 让写入 NULL 直接失败。

**`DEFAULT` 可以是表达式**：

```sql
created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP     -- 当前时间
updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
uuid_col    VARCHAR(36) NOT NULL DEFAULT gen_random_uuid()   -- PostgreSQL 13+ 内建；旧版本需装 pgcrypto 扩展
seq_no      INTEGER NOT NULL DEFAULT 0
code        VARCHAR(20) NOT NULL DEFAULT concat('U', nextval('user_seq'))  -- 部分数据库允许
```

**关于"自动更新时间戳"**：很多数据库有特殊语法：

```sql
-- PostgreSQL：需要触发器才能实现"UPDATE 时自动更新"
-- MySQL：有 ON UPDATE 子句
updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

-- SQL Server：有 ROWVERSION / 触发器
-- 可移植的做法：在应用层或触发器里显式设置 updated_at
```

**注意 PostgreSQL 没有 `ON UPDATE CURRENT_TIMESTAMP`**，必须写触发器函数。这是一个从 MySQL 迁移到 PostgreSQL 时必踩的坑。

### 3.3 `PRIMARY KEY` 主键

**主键 = `UNIQUE` + `NOT NULL`**，并且一张表只能有一个主键。

```sql
-- 单列主键
CREATE TABLE students (
    student_id INTEGER PRIMARY KEY        -- 隐含 NOT NULL 和 UNIQUE
);

-- 复合主键（表级）
CREATE TABLE enrollments (
    student_id INTEGER NOT NULL,
    course_id  INTEGER NOT NULL,
    semester   VARCHAR(20) NOT NULL,
    PRIMARY KEY (student_id, course_id, semester)     -- 三列共同唯一
);
```

**复合主键的语义**：`(student_id, course_id, semester)` 这个**组合**必须唯一，但每一列可以重复。**这与"三个列各自唯一"完全不同**，是初学者容易误解的地方。

**代理键 (surrogate key) vs 自然键 (natural key)**：

| | 代理键 | 自然键 |
| --- | --- | --- |
| 是什么 | 与业务无关的人工编号（自增 ID、UUID） | 业务上本来就有唯一性的字段（学号、身份证号、ISBN） |
| 优点 | 稳定不变、简洁、索引效率高 | 不需要额外列、语义明确、无需 JOIN 就能理解 |
| 缺点 | 需要额外列；对外暴露时会泄露"数据量"等信息 | **业务规则可能变化**（学号规则改了、邮箱可改、身份证升级） |
| 变更的代价 | 无（它本来就不含业务含义） | **高**：主键变了，所有引用它的外键都要级联更新 |

**实践建议**：**大多数场景用代理键**（自增 `BIGINT` 或 UUID），同时给自然键加 `UNIQUE` 约束。这样既有稳定的主键，又保证了业务唯一性。

```sql
CREATE TABLE users (
    user_id    BIGINT       PRIMARY KEY,          -- 代理键
    email      VARCHAR(255) NOT NULL UNIQUE,      -- 自然键，加唯一约束
    username   VARCHAR(50)  NOT NULL UNIQUE,
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**自增键 vs UUID**：

| | 自增整数 | UUID |
| --- | --- | --- |
| 空间 | 8 字节 | 16 字节（存储为 `uuid` 类型）或 36 字节（字符串） |
| 索引效率 | **好**（顺序增长，插入集中在索引末尾） | **差**（随机分布，插入会分散在索引各处，造成页分裂） |
| 分布式友好 | ❌ 需要协调（多节点会冲突） | ✅ 各节点独立生成 |
| 可枚举 | ⚠️ 可以猜（`/user/1`、`/user/2`），有信息泄露风险 | ✅ 不可猜 |
| 调试友好 | ✅ 短、好读 | ❌ 长、难念 |

**关于"随机 UUID 影响索引性能"**：这是真实存在的问题。缓解方式：

- 用**有序 UUID**（UUIDv7、ULID、Snowflake ID），它们把时间戳放在前面，因此大致按时间递增，索引局部性好得多；
- 或者用 UUID 作为业务标识，但**主键仍然是自增整数**。

> 我在这里只描述这个权衡的方向，不推荐具体的库或版本——需要时请查你所用的数据库与语言生态当前支持什么。

### 3.4 `UNIQUE` 唯一约束

```sql
CREATE TABLE students (
    student_id INTEGER PRIMARY KEY,
    email      VARCHAR(255) UNIQUE,               -- 列级
    id_card    VARCHAR(18),
    UNIQUE (id_card),                             -- 表级（等价）
    UNIQUE (major, city)                          -- 复合唯一
);
```

**`UNIQUE` 与 `PRIMARY KEY` 的区别**：

| | `PRIMARY KEY` | `UNIQUE` |
| --- | --- | --- |
| 数量 | 每表**最多 1 个** | 可以有多个 |
| 允许 `NULL` | ❌ 不允许（隐含 `NOT NULL`） | ✅ **允许** |
| 多个 `NULL` 是否冲突 | — | **不冲突**（标准行为，主流数据库都遵守） |
| 用途 | 行的唯一标识 | 保证业务字段不重复 |

**"多个 `NULL` 在 `UNIQUE` 列上不冲突"这一点必须理解**：

```sql
CREATE TABLE users (
    user_id BIGINT PRIMARY KEY,
    email   VARCHAR(255) UNIQUE          -- 允许 NULL
);

INSERT INTO users VALUES (1, 'a@example.com');
INSERT INTO users VALUES (2, NULL);      -- ✅ 可以
INSERT INTO users VALUES (3, NULL);      -- ✅ 也可以！
INSERT INTO users VALUES (4, 'a@example.com');  -- ❌ 报唯一冲突
```

**原因**：`UNIQUE` 检查的是"是否存在另一个值与之相等"。而 `NULL = NULL` 是 `UNKNOWN`，**无法判定为"相等"**，所以不构成冲突。这与 `GROUP BY` / `DISTINCT` 把 NULL 归为一组并不矛盾（前者判断"是否相等"，后者是"如何分组"）。

**这个行为有时会带来麻烦**：如果你希望"同一列上最多只有一个 NULL"，标准 `UNIQUE` 做不到。常见的处理方式：

```sql
-- 部分索引 (partial index)：只对非 NULL 的行建唯一索引
-- PostgreSQL 支持；SQLite 也支持部分索引
CREATE UNIQUE INDEX uq_users_email_notnull ON users (email) WHERE email IS NOT NULL;
-- 在 PostgreSQL 里，普通 UNIQUE 索引本来就不索引 NULL 行，所以效果类似；
-- 但用 WHERE 显式表达意图更清楚。

-- 另一种做法：允许 NULL，用应用层逻辑保证"只有一个 NULL"
-- 或者用 COALESCE 配合表达式索引（各数据库支持程度不同）
```

**复合唯一约束的业务含义**（`enrollments` 的例子）：

```sql
UNIQUE (student_id, course_id, semester)
-- 保证：同一学生在同一学期不会重复选同一门课
-- 但允许：同一学生在不同学期重复选同一门课（比如重修）
-- 也允许：不同学生选同一门课
```

**这是"复合唯一"最典型的用法**：把"业务的唯一性"翻译成一列组合的约束，让数据库帮你挡住重复数据，而不是靠应用层去查一遍再插（那样在并发下有竞态）。

### 3.5 `FOREIGN KEY` 外键

外键保证**引用完整性 (referential integrity)**：子表里的值必须在上表中存在。

```sql
CREATE TABLE courses (
    course_id  INTEGER PRIMARY KEY,
    course_name VARCHAR(100) NOT NULL,
    teacher_id INTEGER REFERENCES teachers (teacher_id)   -- 列级外键
);

-- 或者表级，带显式名字和删除策略
CREATE TABLE enrollments (
    enrollment_id INTEGER PRIMARY KEY,
    student_id    INTEGER NOT NULL,
    course_id     INTEGER NOT NULL,
    CONSTRAINT fk_enroll_student
        FOREIGN KEY (student_id) REFERENCES students (student_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    CONSTRAINT fk_enroll_course
        FOREIGN KEY (course_id)  REFERENCES courses (course_id)
        ON DELETE RESTRICT
);
```

**`ON DELETE` / `ON UPDATE` 的行为对比**：

| 动作 | 删除/更新被引用的父行时 |
| --- | --- |
| `NO ACTION`（默认） | 如果在事务结束前仍有引用，报错。**允许在事务内"先删父再删子"** |
| `RESTRICT` | **立即**报错，不允许任何延迟 |
| `CASCADE` | **级联**删除/更新所有子行 |
| `SET NULL` | 把子表的外键列设为 `NULL`（该列必须允许 NULL） |
| `SET DEFAULT` | 把子表的外键列设为它的默认值（该默认值必须存在于父表） |

**`NO ACTION` 与 `RESTRICT` 的区别**（一个真实的细节）：两者都"报错"，但 `RESTRICT` **立即检查**，`NO ACTION` 允许把检查推迟到事务结束（如果约束声明为 `DEFERRABLE`）。所以：

```sql
-- 用 NO ACTION（默认）时，在同一个事务里这样做是允许的
BEGIN;
DELETE FROM students WHERE student_id = 1;
DELETE FROM enrollments WHERE student_id = 1;    -- 事务结束前清掉了引用
COMMIT;                                          -- ✅ 成功

-- 用 RESTRICT 时，第一条 DELETE 就会立即报错
```

**这个细节在实践中很重要**：如果你希望"删除父行必须显式先删子行"，用 `RESTRICT`（更严格）；如果你希望"事务内可以自由调整顺序"，用 `NO ACTION`。

**外键列上的索引 —— 一个必须知道的方言差异**：

| 数据库 | 是否自动为外键列建索引 |
| --- | --- |
| **MySQL (InnoDB)** | ✅ **自动创建**（这是外键约束的硬性要求） |
| **PostgreSQL** | ❌ **不会！必须手工建** |
| SQLite | ❌ 不会（而且需要 `PRAGMA foreign_keys = ON` 才启用外键检查） |
| SQL Server | ❌ 不会（但会提示） |
| Oracle | ❌ 不会 |

**这个差异有实际后果**：从 MySQL 转到 PostgreSQL 时，很多人以为"外键列上有索引"，实际上没有。而没有索引的外键列会导致：

1. **删除父行很慢**（数据库要扫描整个子表确认没有引用）；
2. **按外键列连接/查询子表很慢**。

```sql
-- PostgreSQL 上建外键后应该补索引
CREATE INDEX idx_enrollments_student ON enrollments (student_id);
CREATE INDEX idx_enrollments_course  ON enrollments (course_id);
```

**关于 SQLite 的一个坑**：SQLite **默认不启用外键约束检查**！必须对每个连接执行：

```sql
PRAGMA foreign_keys = ON;
```

**否则外键只是写在 schema 里，完全不生效。** 这是 SQLite 的一个真实特性，很多人以为外键在工作，其实没有。

**自引用外键**（层级结构）：

```sql
CREATE TABLE employees (
    emp_id     INTEGER PRIMARY KEY,
    emp_name   VARCHAR(50) NOT NULL,
    manager_id INTEGER REFERENCES employees (emp_id)     -- 指向同一张表
);
-- 顶层节点的 manager_id 为 NULL（没有上级）
```

**外键与性能的权衡**：外键在每次写入时都要检查父表（需要一次索引查找），所以**有写入开销**。在高并发写入场景下，有些系统会**去掉外键约束、改由应用层保证**。这是一个真实的权衡：

| 保留外键 | 去掉外键 |
| --- | --- |
| ✅ 数据库层面保证一致性，不会出现孤儿数据 | ❌ 一致性完全依赖应用代码，容易漏 |
| ✅ 读代码时能直接看到表间关系 | ❌ 关系只存在于文档/代码里 |
| ❌ 写入有额外检查开销 | ✅ 写入更快 |
| ❌ 级联删除可能失控（删一行连带删掉几万行） | ✅ 删除行为完全由应用控制 |
| ❌ 大表加外键需要长时间校验现有数据 | — |

**我的看法**：**默认应该保留外键**，除非有明确测得的性能瓶颈。放弃数据一致性的代价通常比那点写入开销大得多。如果要放弃，必须配套严格的应用层约束与定期的数据一致性检查。

### 3.6 `CHECK` 检查约束

`CHECK` 接受一个布尔表达式，插入/更新时必须满足（或为 `UNKNOWN`）。

```sql
CREATE TABLE enrollments (
    enrollment_id INTEGER PRIMARY KEY,
    score         NUMERIC(5,2) CHECK (score >= 0 AND score <= 100),
    semester      VARCHAR(20)  NOT NULL CHECK (semester ~ '^[0-9]{4}-(Spring|Fall)$')  -- 正则，PostgreSQL 语法
);

-- 表级 CHECK（可以涉及多列）
CREATE TABLE date_ranges (
    id         INTEGER PRIMARY KEY,
    start_date DATE NOT NULL,
    end_date   DATE NOT NULL,
    CONSTRAINT chk_date_order CHECK (end_date >= start_date)     -- 跨列检查
);
```

**`CHECK` 与 `NULL` 的关系（必须理解）**：如果检查表达式的结果是 `UNKNOWN`，约束**不阻止**插入。因为约束只在"表达式为 `FALSE`"时报错，`UNKNOWN` 被当作"无法判定为违反"。

```sql
CREATE TABLE t (
    score NUMERIC(5,2) CHECK (score >= 0 AND score <= 100)
);

INSERT INTO t VALUES (150);    -- ❌ 报错（150 <= 100 是 FALSE）
INSERT INTO t VALUES (NULL);   -- ✅ 允许！（NULL >= 0 是 UNKNOWN，约束不阻止）
INSERT INTO t VALUES (-1);     -- ❌ 报错
```

**所以 `CHECK` 不能替代 `NOT NULL`。** 想同时保证"非空且在范围内"，必须写两个约束：

```sql
score NUMERIC(5,2) NOT NULL CHECK (score >= 0 AND score <= 100)
```

**MySQL 的一个重要历史事实**：**MySQL 在 8.0.16 之前会解析但静默忽略 `CHECK` 约束**。也就是说在旧版本上，你写了 `CHECK (score <= 100)`，它创建成功，但**不生效**。8.0.16 起 MySQL 真正强制执行 `CHECK`。

| 数据库 | `CHECK` 是否强制执行 |
| --- | --- |
| PostgreSQL | ✅ 强制执行 |
| SQLite | ✅ 强制执行 |
| MySQL 8.0.16+ | ✅ 强制执行 |
| **MySQL 8.0.16 之前** | ❌ **解析但忽略**（历史上最大的"以为有约束其实没有"陷阱之一） |
| Oracle | ✅ 强制执行 |

**从 MySQL 迁移或读旧代码时，遇到 `CHECK` 要确认它是否真的在生效**——可以试着插入一条违反约束的数据验证。

**`CHECK` 与 `ENUM` 的取舍**：

```sql
-- ✅ CHECK + VARCHAR：可移植，加新值只需改约束
status VARCHAR(20) NOT NULL CHECK (status IN ('pending', 'active', 'cancelled'))

-- MySQL 的 ENUM：写起来短，但加值需要 ALTER TABLE（在大表上代价高），且不是标准 SQL
status ENUM('pending', 'active', 'cancelled') NOT NULL
```

**建议用 `CHECK` + `VARCHAR`**：可移植、修改灵活。代价是存储稍大（`VARCHAR` vs `ENUM` 的整数编码），但这个差异通常不值得为它牺牲灵活性。

### 3.7 约束总表

| 约束 | 保证 | 是否允许多个 | 允许 NULL |
| --- | --- | --- | --- |
| `NOT NULL` | 列必须有值 | — （列属性） | ❌ |
| `DEFAULT` | 列缺省时的填充值 | — （列属性，每列一个） | — |
| `PRIMARY KEY` | 唯一 + 非空，行的标识 | 每表 1 个 | ❌ |
| `UNIQUE` | 值（或组合）不重复 | 多个 | ✅（多个 NULL 不冲突） |
| `FOREIGN KEY` | 引用完整性 | 多个 | ✅（但引用 `NULL` 时不检查） |
| `CHECK` | 满足布尔表达式 | 多个 | ✅（表达式为 UNKNOWN 时不阻止） |

**关于 `FOREIGN KEY` 与 `NULL` 的一个说明**：如果外键列是 `NULL`，**引用检查被跳过**（因为 `NULL` 不指向任何行）。这是 SQL 标准的行为。所以一个"可以为 NULL 的外键"意味着"这一列可以没有引用"，这在业务上通常是合理的（例如 `courses.teacher_id` 为 NULL 表示"还没分配老师"）。

## 4. `ALTER TABLE` 与 `DROP TABLE`

```sql
-- 加列（可以带默认值）
ALTER TABLE students ADD COLUMN phone VARCHAR(20);
ALTER TABLE students ADD COLUMN is_active BOOLEAN NOT NULL DEFAULT TRUE;

-- 删列
ALTER TABLE students DROP COLUMN phone;

-- 改类型 / 改可空性
ALTER TABLE students ALTER COLUMN major TYPE VARCHAR(100);
ALTER TABLE students ALTER COLUMN city SET NOT NULL;
ALTER TABLE students ALTER COLUMN city DROP NOT NULL;

-- 改默认值
ALTER TABLE students ALTER COLUMN enroll_year SET DEFAULT 2025;
ALTER TABLE students ALTER COLUMN enroll_year DROP DEFAULT;

-- 重命名（方言差异大）
ALTER TABLE students RENAME TO pupils;                   -- 表名
ALTER TABLE students RENAME COLUMN name TO full_name;    -- 列名（PostgreSQL / 较新 MySQL 支持）
-- MySQL 8.0 起支持 RENAME COLUMN；更早版本要用 CHANGE COLUMN 并重复整个列定义

-- 加/删约束
ALTER TABLE enrollments ADD CONSTRAINT chk_score CHECK (score >= 0 AND score <= 100);
ALTER TABLE enrollments DROP CONSTRAINT chk_score;
ALTER TABLE enrollments ADD CONSTRAINT fk_enroll_student
    FOREIGN KEY (student_id) REFERENCES students (student_id);
ALTER TABLE enrollments DROP CONSTRAINT fk_enroll_student;

-- 删表
DROP TABLE students;                    -- 如果被外键引用会失败
DROP TABLE IF EXISTS students;          -- 不存在也不报错
DROP TABLE students CASCADE;            -- PostgreSQL：连依赖它的对象一起删（⚠️ 危险）
DROP TABLE students RESTRICT;           -- 有依赖就拒绝（默认行为）
```

**`DROP TABLE` 与 `TRUNCATE` 的区别**：

| | `DROP TABLE` | `TRUNCATE TABLE` |
| --- | --- | --- |
| 删什么 | 表结构 + 数据 + 索引 + 约束 | **只删数据**，结构保留 |
| 能否回滚 | DDL，通常不能（PostgreSQL 可以） | 视数据库与事务支持（PostgreSQL 可以；MySQL 的 `TRUNCATE` 是 DDL，不能回滚） |
| 速度 | 快 | **很快**（通常不写 undo/redo 日志的逐行记录） |
| 触发器 | 不触发 | 通常不触发行级触发器 |
| 自增计数器 | 一并消失 | **会被重置** |

### 4.1 `ALTER TABLE` 在大表上的风险

**这是一个真实的、会造成生产事故的问题**：有些 `ALTER TABLE` 操作需要**重写整张表**，期间可能长时间持有排他锁。

| 操作 | 通常是否需要重写表 |
| --- | --- |
| 加一个可为 NULL 的列（无默认值） | 通常不需要（只改元数据） |
| 加一个 `NOT NULL DEFAULT` 的列 | **可能需要**（各数据库不同；PostgreSQL 11+ 对常量默认值做了优化，不再重写） |
| 改列类型 | **通常需要**（尤其涉及类型转换） |
| 加索引 | 需要扫描全表建索引，但仍可读写（视数据库与是否用 `CONCURRENTLY`） |
| 加外键约束 | 需要校验现有数据（全表扫描） |
| 改列可空性 | 视情况 |

**缓解手段**（只描述方向，具体语法按数据库查文档）：

- **在线 DDL / 并发 DDL**：部分数据库提供不锁表的 DDL 机制。例如 PostgreSQL 的 `CREATE INDEX CONCURRENTLY`、MySQL 8.0 的 `ALGORITHM=INPLACE` / `ALGORITHM=INSTANT`。**注意 `CREATE INDEX CONCURRENTLY` 不能放在事务块里**（这是一个真实的限制）。
- **分批操作**：加约束时先加 `NOT VALID`（PostgreSQL），之后单独校验，避免一次性长时间锁表。
- **影子表 / 在线改表工具**：先建新表、逐步同步数据、最后原子切换。
- **在低峰期执行**，并提前估算耗时（大表上改类型可能几小时）。

**实践建议**：**任何在生产库上的 `ALTER TABLE` 都应该先在等价数据量的测试库上跑一遍，测量锁持有时间**。不要凭"这条语句看起来很简单"就执行。

## 5. 索引基础

### 5.1 索引是什么，为什么能加速

**索引是一种额外的数据结构，用来加速"按某个条件找行"。** 最常见的实现是 **B+ 树 (B+ tree)**。

没有索引时，`WHERE student_id = 12345` 必须**全表扫描 (full table scan / sequential scan)**：逐行检查，代价 O(n)。

有索引时，B+ 树提供 O(log n) 的查找：从根往下几层就能定位到目标。

```text
                      [ 100 | 200 | 300 ]           ← 内部节点（只存键与指针）
                     /      |      |      \
                    /       |      |       \
        [10|50|90]  [120|150]  [210|250]  [310|390]   ← 叶子层
           ↓            ↓          ↓          ↓
      指向实际行的指针（或行本身，见"聚簇索引"）
```

代价是：

- **额外空间**：索引本身要占磁盘（通常比表小，但对宽表+多索引可能很可观）；
- **写入变慢**：每次 `INSERT` / `UPDATE` / `DELETE` 都要同步维护索引。

**所以"索引越多越好"是错的**：读快与写快之间存在权衡。

### 5.2 创建索引

```sql
-- 普通索引
CREATE INDEX idx_students_major ON students (major);
CREATE INDEX idx_enrollments_student ON enrollments (student_id);

-- 唯一索引（相当于加了一个 UNIQUE 约束，但可以在已有表上加）
CREATE UNIQUE INDEX uq_students_email ON students (email);

-- 复合索引（列的顺序有意义！）
CREATE INDEX idx_enroll_student_semester ON enrollments (student_id, semester);

-- 部分索引（只索引满足条件的行，索引更小更快）
-- PostgreSQL / SQLite 支持
CREATE INDEX idx_enroll_high_scores ON enrollments (student_id) WHERE score >= 90;

-- 表达式索引（对函数结果建索引）
-- PostgreSQL 支持
CREATE INDEX idx_students_name_lower ON students (LOWER(name));

-- 并发建索引（不长时间阻塞写入）
-- PostgreSQL
CREATE INDEX CONCURRENTLY idx_big_table_col ON big_table (col);

-- 删索引
DROP INDEX idx_students_major;
DROP INDEX CONCURRENTLY idx_big_table_col;    -- PostgreSQL
```

### 5.3 索引的命名约定

没有强制的标准，但一个清晰的约定能省很多事：

```text
idx_<表名>_<列名>        普通索引     idx_enrollments_student_id
uq_<表名>_<列名>         唯一索引     uq_users_email
fk_<表名>_<引用表>       外键约束     fk_enrollments_students
pk_<表名>                主键约束     pk_students
chk_<表名>_<规则>        CHECK 约束   chk_enrollments_score_range
```

**统一命名的重要性**：迁移脚本、运维脚本、排查问题时都需要按名字引用约束与索引。名字混乱会造成大量"这个索引是干什么的，能删吗"的困惑。

### 5.4 最左前缀原则 (leftmost prefix rule)

**这是复合索引最重要的规则。**

对于复合索引 `(a, b, c)`，它能服务于**从左开始的连续前缀**：

| 查询条件 | 能否用上索引 `(a, b, c)` |
| --- | --- |
| `WHERE a = ?` | ✅ 能用（前缀 `a`） |
| `WHERE a = ? AND b = ?` | ✅ 能用（前缀 `a,b`） |
| `WHERE a = ? AND b = ? AND c = ?` | ✅ 能用（完整键） |
| `WHERE a = ? AND c = ?` | ⚠️ **只能用 `a` 部分**，`c` 用不上（跳过了 `b`） |
| `WHERE b = ?` | ❌ 用不上（不是从 `a` 开始的前缀） |
| `WHERE b = ? AND c = ?` | ❌ 用不上 |
| `WHERE c = ?` | ❌ 用不上 |

**把索引想成一本按"姓、名"排序的电话簿**：

```text
索引 (last_name, first_name) 相当于电话簿先按姓排序，同姓再按名排序

  ✅ 按姓查           → 能快速定位
  ✅ 按姓+名查        → 能精确定位
  ❌ 只按名查         → 没用！因为名只在同一个姓内部有序，
                        跨姓的名是完全乱序的
```

**一个重要的补充**：范围条件会**截断**后续列的使用：

```sql
-- 索引 (a, b, c)
WHERE a = 1 AND b > 10 AND c = 5
-- a 用于定位，b 用于范围扫描，但 c 【用不上】了
-- 因为在 b > 10 这个范围内，c 并不是有序的
```

**例外（需要准确说明）**：某些数据库有"索引跳跃扫描 (index skip scan)"之类的优化，能在前导列区分度低时部分利用后续列。**这是优化器的能力，不是我们可以依赖的规律**，所以建索引时仍应按最左前缀原则设计。

**实践结论**：**设计复合索引时，把最常用于等值过滤的列放前面，把范围查询的列放后面。** 常见做法是"等值列在前、范围列在后、排序列再后"。

```sql
-- 假设最常见的查询是：
--   SELECT * FROM enrollments WHERE student_id = ? AND semester = ? ORDER BY score DESC
CREATE INDEX idx_enroll_sid_sem_score ON enrollments (student_id, semester, score DESC);
-- 前两列用于等值定位，第三列用于排序（避免额外排序步骤）
```

### 5.5 什么时候索引用不上

这是本篇最实用的一节。**写上索引不等于用上索引。**

#### 情况 1：在索引列上做函数或运算（最常见）

```sql
-- ❌ 用不上 birth_date 上的索引
SELECT * FROM students WHERE YEAR(birth_date) = 2005;
-- 因为索引里存的是 birth_date 的原始值，
-- 而 YEAR(birth_date) 是每行都要算一遍的函数结果，索引对它没有序。

-- ✅ 改写成对原始列的范围比较（索引可用）
SELECT * FROM students
WHERE birth_date >= '2005-01-01' AND birth_date < '2006-01-01';

-- ❌ 同理，这些都用不上索引
WHERE score * 1.1 > 90
WHERE DATE(created_at) = '2025-03-12'
WHERE UPPER(name) = 'ALICE'
WHERE CAST(id AS TEXT) = '123'

-- ✅ 改写
WHERE score > 90 / 1.1
WHERE created_at >= '2025-03-12' AND created_at < '2025-03-13'
WHERE name = 'alice'                       -- 如果数据本身统一小写
-- 或者为 UPPER(name) 建【表达式索引】（PostgreSQL 支持）
CREATE INDEX idx_students_name_upper ON students (UPPER(name));
```

**这是"索引用不上"最常见的原因**，也是最容易修复的（改写查询即可）。

#### 情况 2：`LIKE` 以通配符开头

```sql
-- ❌ 用不上索引（无法确定从哪里开始找）
WHERE course_name LIKE '%数据库%'

-- ✅ 可以用索引（前缀确定）
WHERE course_name LIKE '数据%'
```

需要"包含匹配"时，考虑全文索引或专门的搜索方案。

#### 情况 3：隐式类型转换

```sql
-- 假设 phone 是 VARCHAR，而这里传了数字
-- ❌ 在部分数据库上会导致隐式转换，索引用不上
SELECT * FROM users WHERE phone = 13800138000;

-- ✅ 类型匹配
SELECT * FROM users WHERE phone = '13800138000';
```

**注意这个行为因数据库而异**：MySQL 在字符串与数字比较时会做隐式转换（可能导致索引失效，也可能不会，取决于哪一侧被转换），而 PostgreSQL **更严格**——类型不匹配会直接报错，不会静默转换。**结论：让应用传入的类型与列类型一致，不要依赖隐式转换。**

#### 情况 4：`OR` 连接不同列

```sql
-- 索引 (major) 和 (city) 分别存在
-- ❌ 部分数据库无法有效利用索引
SELECT * FROM students WHERE major = '软件工程' OR city = '厦门';

-- ✅ 改写成 UNION（各自都能用上索引）
SELECT * FROM students WHERE major = '软件工程'
UNION
SELECT * FROM students WHERE city = '厦门';

-- ✅ 或者用 IN（同一个列时能走索引）
SELECT * FROM students WHERE major IN ('软件工程', '数据科学');
```

#### 情况 5：选择性低 (low selectivity)

```sql
-- 假设 gender 只有 'M' / 'F' 两个值
CREATE INDEX idx_students_gender ON students (gender);
-- ⚠️ 这个索引基本没用：查询 WHERE gender = 'M' 会返回约一半的行，
--    此时【全表扫描比走索引更快】（因为走索引还要回表，反而更多 I/O）
```

**选择性的概念**：`选择性 = 不同值的个数 / 总行数`。选择性越高（越接近 1），索引越有价值。**性别（2 个值）、布尔标志、状态码（几个值）这类低选择性列上的单列索引通常意义不大。**

**例外**：如果某个低选择性的值**非常罕见**（例如状态列 99% 是 `active`，但你想查 `error`），那么为这个罕见值建**部分索引**是有意义的：

```sql
-- 只索引罕见的那部分
CREATE INDEX idx_orders_errors ON orders (created_at) WHERE status = 'error';
```

#### 情况 6：前置 `%`、`NOT`、`<>`、`IS NOT NULL`、否定条件

这些条件**通常无法有效利用 B+ 树索引**（因为它们需要"排除"大量行，而 B+ 树擅长"定位"）：

```sql
WHERE name NOT LIKE 'A%'
WHERE status <> 'cancelled'
WHERE name IS NOT NULL          -- 如果绝大多数行都非 NULL，走索引没意义
```

**注意 `IS NULL` 是可以用索引的**（如果不为 NULL 的行占大多数，查 NULL 的行用索引很有效），而 `IS NOT NULL` 通常不会。

#### 情况 7：数据量太小

表只有几十行时，全表扫描本来就很快，优化器会**故意不用索引**——这是正确的决策，不是 bug。**不要在小表上纠结索引。**

### 5.6 聚簇索引与非聚簇索引

| | 聚簇索引 (clustered) | 非聚簇索引 (non-clustered / secondary) |
| --- | --- | --- |
| 叶子节点存什么 | **行数据本身** | 指向行位置的引用 |
| 表数据顺序 | **按索引键物理有序** | 与索引无关 |
| 数量 | 每表最多 1 个 | 可有多个 |
| 查找到后 | 直接拿到数据 | **需要"回表"再读一次** |

**"回表 (bookmark lookup)"**：用非聚簇索引找到行的位置后，还要去主数据区再读一次真正需要的列。这就是为什么：

- 索引只覆盖部分列时，查询要付出两次 I/O 的代价；
- **覆盖索引 (covering index)** 能避免回表。

**MySQL InnoDB 的具体行为**（这是准确的事实）：InnoDB 的表本身就是**按主键组织的聚簇索引**（主键索引的叶子就是行数据）；所有二级索引的叶子存的是**主键值**，所以通过二级索引查非索引列时，要先查二级索引拿到主键，再查主键索引拿数据——**这正是 InnoDB 里"回表"的确切含义**。

**PostgreSQL 的具体行为**：PostgreSQL 默认**所有索引都是非聚簇的**（索引叶子存的是行在堆表里的物理位置 `ctid`）。它有一个 `CLUSTER` 命令可以**一次性**按某个索引重排表数据，但**后续的写入不会维持这个顺序**（所以 `CLUSTER` 是一个手动维护的操作，不是持续属性）。

**理解这个差异的价值**：它解释了为什么"我加了一个索引，但这个查询还是很慢"——因为它可能只需要回表太多次。这也引出了下面这条很实用的技巧。

### 5.7 覆盖索引 (covering index)

**如果一个查询需要的所有列都在索引里，数据库就不需要回表。**

```sql
-- 索引包含 student_id 和 semester
CREATE INDEX idx_enroll_sid_sem ON enrollments (student_id, semester);

-- ✅ 这个查询只需要这两列，可以完全从索引得到答案（index-only scan）
SELECT student_id, semester FROM enrollments WHERE student_id = 1;

-- ⚠️ 这个查询还需要 score，所以要回表
SELECT student_id, semester, score FROM enrollments WHERE student_id = 1;

-- ✅ 把 score 也加进索引，让它成为覆盖索引
CREATE INDEX idx_enroll_sid_sem_score ON enrollments (student_id, semester, score);
```

**权衡**：把更多列放进索引 → 更多查询可以"免回表"，但**索引变大、写入更慢**。

**关于"该不该为了覆盖索引把列都塞进去"**：应该针对**真正高频且性能敏感**的查询做这个优化。**不要为每个查询都建一个覆盖索引**——索引空间与写入开销会迅速失控。部分数据库支持 `INCLUDE` 子句把"只用于覆盖、不参与排序/查找"的列排除在索引键之外：

```sql
-- PostgreSQL 11+ / SQL Server：INCLUDE 列只存在于叶子节点，不参与索引排序
CREATE INDEX idx_enroll_sid_sem_incl ON enrollments (student_id, semester) INCLUDE (score);
```

这样索引键保持精简（查找效率高），同时又能覆盖查询。

### 5.8 `EXPLAIN`：不要猜，去看执行计划

```sql
-- 只显示预估计划（不真正执行）
EXPLAIN SELECT * FROM enrollments WHERE student_id = 1;

-- 真正执行并给出实际耗时与行数（PostgreSQL / MySQL 8+）
EXPLAIN ANALYZE SELECT * FROM enrollments WHERE student_id = 1;

-- MySQL 的另一种详细格式
EXPLAIN FORMAT=JSON SELECT ...;
EXPLAIN FORMAT=TREE SELECT ...;
```

**该看什么（关注点，而不是具体字段名）**：

| 关注点 | 说明 |
| --- | --- |
| **访问方式** | 出现 "Seq Scan"/"ALL"/"full table scan" 说明没用上索引；出现 "Index Scan"/"ref"/"range" 说明用了 |
| **预估行数 vs 实际行数** | 差得太多说明**统计信息过期**，优化器可能选错计划（解决：`ANALYZE` / `ANALYZE TABLE`） |
| **连接算法** | Nested Loop / Hash Join / Merge Join。**两个大表的 Nested Loop 通常是性能警报** |
| **是否有排序** | "Sort" / "Using filesort" 说明排序没被索引满足 |
| **是否有临时表** | "Using temporary" 在大数据量下是瓶颈 |
| **过滤下推** | `WHERE` 条件是否被下推到扫描阶段（越早过滤越好） |
| **回表次数** | 是否显示需要回到主表读取（例如 "Heap Fetches"） |

**`EXPLAIN` 输出的格式因数据库与版本差异很大**（MySQL 8 与 5.7 明显不同，PostgreSQL 各版本也有变化）。**不要背格式，理解上面这些关注点，然后查你所用的版本的文档。**

**关于统计信息**：优化器依赖**统计信息 (statistics)** 来估算"这个条件会返回多少行"。统计信息过期会导致错误的计划：

```sql
-- PostgreSQL
ANALYZE students;

-- MySQL
ANALYZE TABLE students;

-- 现代数据库多数有自动统计信息收集（autovacuum 等），
-- 但大批量导入数据后手工 ANALYZE 一次往往是必要的。
```

### 5.9 索引使用检查清单

| # | 检查项 |
| --- | --- |
| 1 | 索引列上有没有函数或运算？（有 → 改写查询或建表达式索引） |
| 2 | 复合索引的列顺序是否匹配最左前缀？等值列在前、范围列在后 |
| 3 | `LIKE` 是否以 `%` 开头？ |
| 4 | 比较的类型是否与列类型一致（避免隐式转换）？ |
| 5 | 是否用了 `OR` 连接不同列？（考虑改 `UNION`） |
| 6 | 索引列的选择性是否足够（低选择性列的索引意义不大）？ |
| 7 | 是否有不必要的索引（只增写入开销）？ |
| 8 | 外键列在 PostgreSQL 上补索引了吗？ |
| 9 | 统计信息是否是最新的（`ANALYZE`）？ |
| 10 | 高频查询是否可以用覆盖索引免回表？ |
| 11 | 用 `EXPLAIN` 验证过实际计划吗？（不要靠猜） |

## 6. `VIEW` 简介

**视图是一个命名的查询，不存储数据**（普通视图不存储；物化视图则存储，见下）。

```sql
CREATE VIEW student_course_summary AS
SELECT s.student_id,
       s.name       AS student_name,
       s.major,
       c.course_name,
       e.score,
       e.semester
FROM enrollments e
JOIN students s ON s.student_id = e.student_id
JOIN courses  c ON c.course_id  = e.course_id;

-- 使用起来像表一样
SELECT * FROM student_course_summary WHERE score >= 90;

-- 修改定义
CREATE OR REPLACE VIEW student_course_summary AS ...;
-- 或者先 DROP VIEW 再 CREATE

-- 删除
DROP VIEW student_course_summary;
```

**视图的价值**：

| 价值 | 说明 |
| --- | --- |
| **简化复杂查询** | 把三表连接封装成一个"虚拟表"，使用者只需 `SELECT * FROM view WHERE ...` |
| **隐藏敏感列** | 可以只暴露部分列（例如视图里不含身份证号），配合权限控制实现列级安全 |
| **稳定接口** | 底层表结构调整时，只要让视图保持原样，依赖视图的应用代码不用改 |
| **统一业务口径** | 把"有效订单"的定义写进视图，避免每个查询各写一遍 |

**视图的限制**：

- **普通视图不存储数据**，每次查询视图都会**展开成底层查询再执行**。所以它**不提升性能**（有时因为嵌套反而让优化器难以优化）；
- 多数数据库的视图是**只读**的（简单的单表视图可能允许更新，但带 JOIN/聚合/`DISTINCT` 的视图通常不能直接 `INSERT`/`UPDATE`）；
- 视图**依赖底层表的列名**。重命名底层列可能导致视图失效（`CREATE OR REPLACE VIEW` 时通常会报错提示）。

**物化视图 (materialized view)** 是一个不同的东西：它**真的存储结果**，需要手动或定时刷新：

```sql
-- PostgreSQL
CREATE MATERIALIZED VIEW course_stats AS
SELECT course_id, COUNT(*) AS n, AVG(score) AS avg_score
FROM enrollments GROUP BY course_id;

REFRESH MATERIALIZED VIEW course_stats;
REFRESH MATERIALIZED VIEW CONCURRENTLY course_stats;    -- 刷新时不阻塞读（需要唯一索引）
```

| | 普通视图 | 物化视图 |
| --- | --- | --- |
| 是否存数据 | ❌ | ✅ |
| 数据新鲜度 | **总是最新** | 取决于上次刷新时间 |
| 查询性能 | 与直接写查询相同 | **快**（数据已算好） |
| 写入开销 | 无 | 刷新时有 |
| 支持情况 | 所有数据库 | **PostgreSQL、Oracle 支持；MySQL 不支持** |

**选择原则**：需要"总是最新"用普通视图；需要"快"并且能接受"数据有几十分钟延迟"（如报表、仪表盘）用物化视图。

## 7. 一个完整的建表示例

把本篇的内容综合起来，设计一套表：

```sql
-- 教师表
CREATE TABLE teachers (
    teacher_id   BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    teacher_name VARCHAR(50)  NOT NULL,
    department   VARCHAR(50)  NOT NULL,
    email        VARCHAR(255) NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_teachers_email UNIQUE (email),
    CONSTRAINT chk_teachers_dept CHECK (length(department) > 0)
);

-- 课程表
CREATE TABLE courses (
    course_id    BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    course_code  VARCHAR(20)  NOT NULL,
    course_name  VARCHAR(100) NOT NULL,
    credits      SMALLINT     NOT NULL,
    teacher_id   BIGINT       REFERENCES teachers (teacher_id) ON DELETE SET NULL,
    is_active    BOOLEAN      NOT NULL DEFAULT TRUE,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_courses_code    UNIQUE (course_code),
    CONSTRAINT chk_courses_credit CHECK (credits BETWEEN 1 AND 10)
);

-- 学生表
CREATE TABLE students (
    student_id  BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_no  VARCHAR(20)  NOT NULL,
    name        VARCHAR(50)  NOT NULL,
    gender      CHAR(1),
    birth_date  DATE,
    major       VARCHAR(50)  NOT NULL,
    city        VARCHAR(50),
    enroll_year SMALLINT     NOT NULL,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_students_no  UNIQUE (student_no),
    CONSTRAINT chk_students_sex CHECK (gender IN ('M', 'F') OR gender IS NULL),
    CONSTRAINT chk_students_year CHECK (enroll_year BETWEEN 2000 AND 2100)
);

-- 选课表（关联表 + 成绩）
CREATE TABLE enrollments (
    enrollment_id BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id    BIGINT       NOT NULL,
    course_id     BIGINT       NOT NULL,
    score         NUMERIC(5,2),
    semester      VARCHAR(20)  NOT NULL,
    enrolled_at   TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_enroll_student FOREIGN KEY (student_id)
        REFERENCES students (student_id) ON DELETE CASCADE,
    CONSTRAINT fk_enroll_course  FOREIGN KEY (course_id)
        REFERENCES courses (course_id)  ON DELETE RESTRICT,
    CONSTRAINT uq_enroll         UNIQUE (student_id, course_id, semester),
    CONSTRAINT chk_enroll_score  CHECK (score IS NULL OR (score >= 0 AND score <= 100)),
    CONSTRAINT chk_enroll_sem    CHECK (semester ~ '^[0-9]{4}-(Spring|Fall|Summer)$')
);

-- 索引：外键列（PostgreSQL 不会自动建！）、高频查询条件
CREATE INDEX idx_courses_teacher      ON courses (teacher_id);
CREATE INDEX idx_enrollments_student  ON enrollments (student_id);
CREATE INDEX idx_enrollments_course   ON enrollments (course_id);
CREATE INDEX idx_enrollments_semester ON enrollments (semester, course_id);
CREATE INDEX idx_students_major_city  ON students (major, city);
```

**这个 schema 里的每个设计决定及其理由**：

| 决定 | 理由 |
| --- | --- |
| `BIGINT` 主键 + `IDENTITY` | 有余量；`IDENTITY` 是标准写法（比 `SERIAL` 更明确） |
| 自然键（`student_no`、`course_code`、`email`）加 `UNIQUE` | 既保证业务唯一，又不用它当主键（避免业务规则变化时改主键） |
| `TIMESTAMPTZ` + `DEFAULT CURRENT_TIMESTAMP` | 统一存 UTC，自动记录创建时间 |
| `score NUMERIC(5,2)` | 精确表示 100 分制、2 位小数（**不用 FLOAT**） |
| `chk_enroll_score` 里写 `score IS NULL OR (...)` | 让约束**允许 NULL**（"未出成绩"），但非 NULL 时必须在范围内。**注意这里显式写了 `IS NULL OR`，因为不加的话 NULL 会因为 UNKNOWN 而自动通过，写出来更清楚** |
| `ON DELETE CASCADE` for student | 删学生时连带删他的选课记录（合理：学生不存在了，选课记录无意义） |
| `ON DELETE RESTRICT` for course | 删课程时如果有选课记录就拒绝（合理：课程被选过就不该被删） |
| `chk_students_sex` 也写了 `OR gender IS NULL` | 显式允许 NULL，意图清楚 |
| 外键列都建了索引 | **PostgreSQL 不会自动建**，没有索引会导致删父行变慢 |
| `idx_enrollments_semester` 是复合索引 `(semester, course_id)` | 假设高频查询是"某学期的课"或"某学期的某课"，按最左前缀设计 |
| 索引不是每个列都建 | 避免写入变慢；只为外键和高频条件建 |

## 8. 常见错误清单

| 错误 | 问题 | 修正 |
| --- | --- | --- |
| 用 `FLOAT`/`DOUBLE` 存金额 | 二进制浮点无法精确表示十进制小数，累加会差分 | 用 `NUMERIC(12,2)` |
| 用 `INT` 存可能超 21 亿的 ID | 溢出；改成 `BIGINT` 的代价很高 | 建表就用 `BIGINT` |
| 以为显式写 `NULL` 会触发 `DEFAULT` | `DEFAULT` 只在"省略该列"时生效 | 省略该列，或写 `DEFAULT` 关键字，或应用层 `COALESCE` |
| 在 MySQL 旧版本依赖 `CHECK` | 8.0.16 之前 `CHECK` 被静默忽略 | 确认数据库版本；必要时用触发器或在应用层校验 |
| 忘了 `CHECK` 不阻止 `NULL` | 想让列非空却只写了 `CHECK` | 同时加 `NOT NULL` |
| 期望 `UNIQUE` 列只允许一个 `NULL` | 多个 `NULL` 不冲突（标准行为） | 用部分唯一索引，或应用层保证 |
| 用复合主键却以为"每列都唯一" | 复合主键保证的是**组合**唯一 | 想每列唯一要各加 `UNIQUE` |
| 在 PostgreSQL 上以为外键列有索引 | PostgreSQL **不会**自动为外键建索引 | 显式 `CREATE INDEX` |
| SQLite 里以为外键在工作 | **默认不启用**外键检查 | 每个连接执行 `PRAGMA foreign_keys = ON` |
| `WHERE YEAR(birth_date) = 2005` | 索引列上用函数，索引失效 | 改成范围比较 `>= '2005-01-01' AND < '2006-01-01'` |
| `WHERE col LIKE '%x%'` | 前置通配符使索引失效 | 考虑全文索引，或改为前缀匹配 |
| 复合索引 `(a,b,c)` 却只查 `b` | 违反最左前缀原则 | 按查询模式调整索引列顺序，或另建索引 |
| 在低选择性列（性别）上建单列索引 | 优化器通常不会用（走索引不如全表扫描） | 删掉，或改用部分索引只索引罕见值 |
| 表上建了太多索引 | 写入变慢、占空间 | 定期审计未使用的索引 |
| 生产库上直接 `ALTER TABLE` 改大表类型 | 可能长时间锁表 | 先在等价数据量的测试库测量；用在线 DDL 或分批方案 |
| 以为视图能提速 | 普通视图不存数据，只是展开查询 | 需要提速用物化视图，或直接优化原查询 |
| 大表上加外键/唯一约束不问耗时 | 需要全表校验，可能很久 | 评估数据量，考虑 `NOT VALID` + 单独校验 |

## 小结

- **DDL 的隐式提交**：MySQL 与 Oracle 不能回滚 DDL；**PostgreSQL / SQLite 可以**。这决定了"改表前是否需要备份"这个纪律。
- **金额、成绩这类数据必须用 `NUMERIC`/`DECIMAL`，绝不用 `FLOAT`/`DOUBLE`**——二进制浮点无法精确表示十进制小数（`0.1 + 0.2 ≠ 0.3`）。或者用整数存最小货币单位。
- `VARCHAR(n)` 里的 `n` 在 **PostgreSQL/MySQL 是字符数，在 Oracle 默认是字节数，SQL Server 的 `VARCHAR` 是字节数**。存中文/emoji 前必须确认，MySQL 推荐 `utf8mb4`。
- **`CHAR` 会补空格**，只在长度严格固定时用。
- 时间存 UTC、显示时转换是最稳的做法。**注意 MySQL 的 `TIMESTAMP` 受时区影响且有 2038 上限**，`DATETIME` 反之；PostgreSQL 用 `TIMESTAMPTZ` 表示带时区。**同一个系统里不要混用带时区和不带时区的列。**
- **主键 = `UNIQUE` + `NOT NULL`，每表最多一个；`UNIQUE` 可以有多个且允许多个 `NULL` 共存**（因为 `NULL = NULL` 是 UNKNOWN，不构成冲突）。
- **优先用代理键（自增 `BIGINT` 或有序 UUID）做主键，把自然键加 `UNIQUE` 约束**——避免业务规则变化时被迫改主键。随机 UUID 会因索引局部性差而拖慢插入，有序 UUID 可缓解。
- **`DEFAULT` 只在"省略该列"时生效**，显式写 `NULL` 不会触发它。要写 `DEFAULT` 关键字或在应用层用 `COALESCE`。
- **`CHECK` 不阻止 `NULL`**（表达式为 UNKNOWN 时不报错），所以 `CHECK` 不能替代 `NOT NULL`。**MySQL 8.0.16 之前会静默忽略 `CHECK`**——遇到旧 MySQL 必须验证约束是否真的生效。
- 外键的 `ON DELETE` 有 `NO ACTION`（可延迟到事务结束）、`RESTRICT`（立即报错）、`CASCADE`、`SET NULL`、`SET DEFAULT` 五种。**`NO ACTION` 与 `RESTRICT` 的区别就在"检查时机"。**
- **PostgreSQL 不会自动为外键列建索引（MySQL 会）**，所以 PostgreSQL 上建完外键要手动补索引。**SQLite 默认不启用外键检查**，需要 `PRAGMA foreign_keys = ON`。
- 外键带来写入开销，去掉它能提升写入性能，但**一致性责任就完全落在应用层**——除非有实测的性能瓶颈，默认应该保留外键。
- **索引用 B+ 树把 O(n) 的全表扫描变成 O(log n) 的查找**，代价是空间与写入变慢。索引不是越多越好。
- **最左前缀原则**：复合索引 `(a,b,c)` 只能服务"从 `a` 开始的连续前缀"；**范围条件会截断后续列的使用**。设计时"等值列在前、范围列在后、排序列再后"。
- **索引用不上的六个主要原因**：索引列上有函数/运算、`LIKE '%x%'`、隐式类型转换、`OR` 连接不同列、选择性太低、表太小（优化器故意不用）。**其中"列上做函数运算"最常见也最容易修（改写成范围比较）。**
- **聚簇索引叶子存行数据（每表最多一个），非聚簇索引需要"回表"**。InnoDB 的主键索引是聚簇的、二级索引叶子存主键值（回表的来源）；PostgreSQL 默认所有索引都是非聚簇的（`CLUSTER` 只是手动重排一次）。
- **覆盖索引**（查询所需列都在索引里）能免回表；但索引变大会拖慢写入。**只为真正高频的查询做这个优化**，必要时用 `INCLUDE` 把"仅用于覆盖"的列排除在索引键外。
- **`ALTER TABLE` 在大表上可能长时间锁表**（改类型、加约束/索引等）。生产环境必须先测量，考虑在线 DDL（如 `CREATE INDEX CONCURRENTLY`，注意它不能在事务块里）或影子表方案。
- **普通视图不存数据、只是展开查询，不会提速**；需要提速用物化视图（**MySQL 不支持**）。
- **用 `EXPLAIN` / `EXPLAIN ANALYZE` 验证，不要猜**。关注"访问方式、预估与实际行数差异、连接算法、有无排序/临时表、是否回表"。**输出格式因数据库与版本差异很大，理解关注点比背格式有用。**
- 大批量导入数据后**手工 `ANALYZE` 一次**，让优化器的统计信息跟上是常见且必要的一步。
